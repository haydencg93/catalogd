# Catalogd: Cast Page Documentation

The Cast & Characters page operates as a highly dynamic, multi-purpose profile hub that seamlessly adapts its data sources, logic, and layout based on the specific type of entity a user requests. Instead of maintaining separate HTML pages for actors, musical artists, authors, and fictional characters, Catalogd centralizes them into a single interface that routes data intelligently based on URL parameters.

## Core Technologies & Services

To achieve its multi-disciplinary scope, the page relies heavily on asynchronous JavaScript, a backend database, and multiple third-party APIs:

* **Supabase:** Manages authentication, custom user artwork (`custom_imgs`), user following logic (`user_characters`), and tier list integrations (`media_lists`, `list_items`).


* **The Movie Database (TMDB):** Supplies biographical and filmography data for actors and film crew via a secure proxy.


* **Wikipedia API:** Used to dynamically scrape summaries and thumbnail images for fictional characters.


* **Open Library API:** Provides author biographies and bibliographies.


* **Last.fm API:** Fetches musician biographies and discographies.



## Initialization & Routing Logic

When `cast.html` loads, `cast.js` immediately parses the URL query parameters using `new URLSearchParams(window.location.search)`. The `initCastPage()` function acts as a router, determining which asynchronous initialization function to trigger based on the presence of specific keys:

1. If `characterWiki` exists, it triggers `initCharacterPage()`.


2. If `authorId` exists, it triggers `initAuthorPage()`.


3. If `personId` exists, it triggers `initPersonPage()` (for TMDB actors/crew).


4. If `artist` exists, it triggers `initArtistPage()`.



## Entity-Specific Data Fetching

Each entity type requires specialized parsing and filtering logic to ensure clean, relevant data is presented to the user.

### Fictional Characters (Wikipedia)

Characters lack a unified global database, so Catalogd relies on the Wikipedia Summary API (`[https://en.wikipedia.org/api/rest_v1/page/summary/](https://en.wikipedia.org/api/rest_v1/page/summary/)...`). Because Wikipedia contains heavily overlapping names, the application employs a **Cascade Fetching** strategy. It attempts three highly specific queries in descending order of strictness:

1. `${wikiId}_(${mediaTitle}_character)`
2. `${wikiId}_(character)`
3. `${wikiId}`

If the API returns a disambiguation page or a "List of..." directory, the script discards it. Furthermore, if it falls back to the generic third query, it cross-references the returned text for keywords like "character", "fictional", or the media title to prevent displaying false positives.

### Authors (Open Library)

When rendering authors, the page pulls from Open Library. The API often returns study guides or workbooks mixed in with an author's actual literature. To combat this, `initAuthorPage()` filters the bibliography against a `noiseKeywords` array (e.g., "sparknotes", "cliffsnote", "study guide"). The data is then deduplicated into a Map based on the title, sorted by publication year, and injected into the DOM.

### Actors & Crew (TMDB)

For film professionals, data is routed through Catalogd's proxy. The script differentiates between actors and crew members by checking `person.known_for_department === 'Acting'`. It then pulls either the `cast` or `crew` array from their combined credits, filtering out entries without poster images. A "Known For" section is dynamically generated by sorting their unique credits by `vote_count`, heavily weighting movies over TV shows.

### Musical Artists (Last.fm)

Artist fetching pulls the top 50 albums and biographical data. Because Last.fm often includes HTML links within its summaries, the script sanitizes the biography by splitting the string at the first `<a href` and returning the clean text.

## Interactive User Features

Regardless of the entity type loaded, the page initializes a shared suite of universal UI components via `setupPersonImage()` and `setupFollowBtn()`.

* **Custom Artwork Override:** Users can replace the default API-provided image with their own URL. When the "Edit Art" button is clicked, `#custom-art-modal` opens. Upon saving, an upsert is performed on the Supabase `custom_imgs` table, and the page reloads to fetch the new image.


* **Following:** Authenticated users can click the "Follow" button to save the person/character to their profile. This toggles a record in the `user_characters` table.


* **Tier List Integration:** The "Add to Tier List" button triggers `setupTierListManager()`. This queries both `media_lists` (lists the user owns) and `list_collaborators` (lists the user is invited to) to present a modal of all eligible tiered lists. Users can seamlessly add or remove the entity from specific lists via the `toggleTierListItem()` global function.



## Responsive Layout Architecture

The user interface uses modern CSS Grid and Flexbox to ensure cross-device compatibility. The main profile header (`#person-header`) naturally displays side-by-side on desktop displays.

To accommodate mobile screens (under 768px), `cast.css` applies a clever CSS restructuring technique. Instead of rewriting the DOM, it uses `display: contents !important` on the `#person-bio-area`. This effectively dissolves the parent container visually, allowing its child elements (the name and the bio) to participate directly in the overarching flex layout. The `order` property is then applied to reposition the character's name *above* their image, while the biography remains below it, creating an optimized vertical reading flow without relying on JavaScript.
